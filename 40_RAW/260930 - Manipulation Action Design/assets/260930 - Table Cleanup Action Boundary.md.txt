# 전체 미션과 책상 정리 Action의 책임 경계 재검토

## 1. 출처

2026-09-30 설계 검증 이후 이어진 사용자와 에이전트의 대화를 요약한다.
이 기록은 KB 재정리의 근거이며 사람 검토를 마친 기술 결정이 아니다.

사용자는 다음 내용을 차례로 질문했다.

- Mission Manager 없이 Action 서버를 먼저 구현할 수 있는가?
- 현재 설계에서는 인식·계획·실행이 다시 Mission Manager를 거치는가?
- 책상 작업 담당자에게 반복을 맡기는 이전 방식과 어느 쪽이 나은가?
- 추천한 책임 경계를 적용하려면 얼마나 변경해야 하는가?

에이전트는 "전체 미션은 Mission Manager, 책상 하나의 작업은 통합 Action 서버"를
추천했고, 사용자는 이어서 **"일단 KB 문서 먼저 다시 정리하자"**고 요청했다.
이는 해당 경계로 문서 초안을 정렬하라는 요청이며, 상세 계약의 확정이나
Decision의 `selected` 승격을 요청한 것으로 해석하지 않는다.

이전 비교 근거는 같은 Raw 폴더의
[최초 작업 흐름 논의](<260928 - Table Cleanup Workflow.md>)와
[Mission Manager FSM 루프 논의](<260930 - Table Cleanup Mission Loop.md>)에 남아 있다.

## 2. 가장 중요한 경계

| 담당 | 대화에서 제안한 책임 |
|---|---|
| Mission Manager | 책상까지 이동 요청, 책상 작업 시작·취소·결과 확인, 복귀와 최종 미션 보고 |
| 책상 정리 Action 서버 | 관측·계획·첫 관측 전달·물체 처리·재관측을 순서대로 조정 |
| Perception | 새 장면과 물체 정보 제공. 다른 점검 기능에서도 독립적으로 호출 가능 |
| Planner | 처리 여부·분류·다음 대상·사람 확인 판단 |
| Skill Executor | 선택된 물체의 집기·들기·운반·놓기와 팔 복귀 |
| Observation Reporter | 같은 장면의 원본 이미지·bbox·라벨·분류를 묶어 전달 |

Action 서버가 Perception이나 Planner를 호출해도 그 알고리즘을 복사하거나
전용 기능으로 바꾸지 않는다. Mission Manager의 미션 상태와 Action 내부 진행 상태는
각 담당자가 관리한다. 패키지 배치와 ROS 필드는 후속 명세에서 검토한다.

## 3. 책상에 도착한 뒤 일어나는 일

```text
Mission Manager가 책상 정리 Goal 한 번 전달
  → 책상 전체 스캔
  → Planner가 분류·처리 여부·순서 판단
  → 첫 물체를 움직이기 전에 원본 이미지와 bbox·라벨·분류 전달
  → 선택한 물체 집기·들기·운반·놓기
  → 새로 스캔하고 다시 판단
  → 더 처리할 대상이 없으면 확인과 결과 정리
  → Mission Manager가 결과를 받아 복귀·보고 판단
```

첫 관측의 이미지와 물체 정보는 같은 촬영 장면이어야 한다. 불확실하거나 위험한
물체는 사람 확인 대상으로 표시하고 자동 조작하지 않는다. 첫 관측 자료의
Backend 저장 확인까지 기다릴지는 미정이며, 현 후보의 발행 성공은 로컬 발행까지다.

## 4. 추천 이유와 변경 범위

- 책상 작업을 하나의 Action으로 요청·시험하고 나중에 Mission Manager와 연결할 수 있다.
- 집은 물체, 놓기 기록, 현재 단계와 단계 재시도를 책상 작업 담당자가 함께 관리할 수 있다.
- Mission Manager에 책상 내부의 스캔 횟수·물체별 skill 순서·snapshot 관리가 들어가는 것을 줄인다.
- 기존 FSM의 직접 호출 경계와 Action 결과를 미션 결과로 바꾸는 계약은 함께 수정해야 한다.

이는 에이전트의 설계 추천이며 두 구조 중 어느 하나만 기술적으로 가능한 것은 아니다.
첫 이미지 전달 순서와 매번 새 plan을 받는 동작도 책상 Action 내부에서 조정할 수 있다.

## 5. 검증에서 드러난 주의점

검증 대화에서 기존 coordinator와 KB의 개수 비교 방식에 다음 반례가 확인됐다.

```text
처음 A·B 관측 → A 처리 → B가 사라지고 새 C 관측 → C 처리 → 빈 책상 확인
```

mock 재현에서는 A·C만 처리했는데 `mission_complete`로 끝났다. 물체 개수만 같다고
B의 처리가 끝났다고 판단할 수 없다는 뜻이다. 구조를 바꾸는 것만으로 해결되지 않으며,
새 관측과 물체별 처리 기록을 연결하는 기준이 필요하다. 실제 로봇 실험 결과는 아니다.

또한 현재 core의 `completed_tasks`는 성공한 skill 이름을 담는다. 집기 성공만으로
물체 처리 완료를 셀 수 없으므로, 성공한 skill과 완료한 task를 구분해야 한다.

## 6. 남은 판단

- 첫 스캔부터 물체가 없을 때 기존 `NO_OBJECTS` 결과와 빈 사진 전달의 관계
- 실패·부분 완료·사람 확인·복귀 실패의 최종 결과와 우선순위
- 취소 요청 후 하위 실행 중단·정지 확인 및 물체를 든 상태의 처리
- 단계 재시도와 책상 Goal 전체 재전송의 조건·중복 제거
- 새 관측의 동일 물체 연결, 종료 확인 횟수와 반복 상한
- 원본 snapshot 보존, 이벤트 ID 유지와 재시작 복구
- 실제 로봇의 놓은 결과 판정 및 수거함 확인을 생략한 경우의 보고
- 최초 Goal의 대상 지정, Planner·Reporter 계약과 서버 패키지 배치

본 기록은 이전 Raw를 덮어쓰지 않는다. 구현 코드와 구현 레포의 상세 명세는
이번 요청의 후속 작업이며 이 Raw 작성만으로 변경되지 않는다.
