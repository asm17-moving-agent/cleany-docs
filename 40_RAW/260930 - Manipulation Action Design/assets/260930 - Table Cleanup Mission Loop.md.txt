# 책상 작업 반복 구조를 Mission Manager FSM 기준으로 맞추는 논의

## 1. 요약

이 문서는 구현 레포의 책상 작업 Action 설계 초안을 기존 Mission Manager FSM과
비교한 대화를 보존하는 **Raw 논의 기록**이다. 사람 검토를 마친 결정이나 구현
완료 사실로 취급하지 않는다.

대화에서 사용자는 재스캔 반복을 **Mission Manager FSM 루프**로 처리하는 안을
선택했다. 종료 재확인과 첫 관측 전달은 대화 중 제시된 제안안을 반영하도록
요청했다. 제안안의 세부 수치와 결과 코드는 사람 검토가 필요하다.

## 2. 배경

구현 레포의 `cleany_skill_executor/docs/`에는 책상 도착 뒤 Mission Manager가
Goal 하나를 보내고 책상 작업 서버가 스캔·처리·재스캔을 반복하는 설계 초안이
있다. 이 구조는 [책상 정리 작업 흐름 논의](<260928 - Table Cleanup Workflow.md>)의
후보에 해당하며, 검토를 마친 Mission Manager FSM의 직접 호출 구조와 다르다.

기존 FSM 구조를 그대로 따를 때 다음 세 가지가 비어 있다는 점을 확인했다.

1. **재스캔 반복이 없다.** FSM은 `PERCEIVE`를 한 번 수행하고 Planner가 만든
   skill sequence를 끝까지 실행한다. 물체 하나를 옮기면 장면이 달라지므로
   다음 물체 판단 전에 다시 관측해야 한다는 요구와 맞지 않는다.
2. **최종 빈 책상 확인이 없다.** 마지막 skill 성공 뒤 바로 `RETURN_HOME`으로
   전이하며, 새 관측으로 처리 대상이 남지 않았는지 확인하지 않는다.
3. **첫 관측 전달 위치가 없다.** 원본 이미지와 bbox는 Perception에, 최종 분류는
   Planner에 있고, 첫 물체를 움직이기 전이라는 순서는 Mission Manager만 보장할
   수 있다.

## 3. 재스캔 반복 위치 비교

| 선택지 | 내용 | 대화에서 확인한 점 |
|---|---|---|
| (a) skill 내부 재관측 | FSM은 유지하고 `pick_object`가 집기 전에 대상을 다시 관측한다. | 첫 관측의 물체 번호로 만든 두 번째 이후 skill은 snapshot이 만료되면 대상을 찾지 못한다. 새 관측과 이전 물체를 연결할 기준이 정해지지 않았다. 새로 드러나거나 밀린 물체를 Planner가 다시 판단할 기회가 없다. |
| (b) FSM 루프 | 처리 대상 하나를 끝내면 `EXECUTE_TASKS`에서 `PERCEIVE`로 돌아간다. | 매 사이클이 새 관측과 새 plan을 사용한다. Perception·Planner·Skill Executor의 경계는 유지된다. Mission Manager가 책상 안의 물체별 반복을 지휘하게 된다. |

구현 레포의 현재 Perception snapshot cache는 최근 2개와 유지 시간 120초를 기본으로
사용한다는 점이 (a)의 제약 근거로 언급됐다. 이는 현재 구현 값이며 제품 기준이 아니다.

**사용자 선택:** (b) FSM 루프.

## 4. 종료 재확인 제안

(b)를 전제로 다음 제안이 제시됐고, 사용자가 반영을 요청했다.

- 처리 대상이 남았는지는 Planner가 판단한다. Mission Manager는 실행할 task가 없는
  plan을 종료 확인 1회로 센다.
- 서로 다른 유효 스캔에서 설정된 횟수만큼 처리 대상이 없음을 확인하면 종료한다.
  횟수와 최대 사이클 수는 설정값이며 기본값은 정하지 않았다.
- 스캔 실패는 확인 횟수에 포함하지 않고 빈 책상으로 판단하지 않는다.
- 이전 사이클에서 처리 대상으로 본 수보다 놓기까지 끝낸 수가 적은 채로 처리
  대상이 사라지면 `SUCCESS`로 보고하지 않는다.
- 첫 사이클에서 물체가 없을 때의 결과는 기존 `NO_OBJECTS` 규칙과 달라질 수 있어
  제품 판단이 필요하다.

## 5. 첫 관측 전달 제안

- 첫 사이클의 `PLAN_TASKS` 성공 뒤, 실행 전에 별도 FSM 상태에서 전달 port를
  호출한다.
- Mission Manager는 snapshot 참조와 plan을 해석하지 않고 전달 port에 넘긴다.
- 전달 port 구현은 event·report 기록 책임 후보인 `cleany_logger`가 맡는 안이
  제시됐다. 같은 snapshot의 원본 이미지를 Perception에서 조회해 bbox·최종 분류와
  묶는다.
- 전달 port의 성공은 로컬 발행까지를 뜻하며 Backend 저장 확인을 뜻하지 않는다.
- 전달에 실패하면 물체를 움직이지 않고 `REPORT`로 전이한다.

Perception이 직접 전달하는 안은 최종 분류가 없어 제외됐다. Planner가 전달하는 안은
계획 책임에 외부 전달이 섞이고 미션 문맥이 필요해 우선순위가 낮았다.

## 6. 남은 판단

- 종료 확인 횟수와 최대 사이클 수의 값
- 첫 사이클 빈 책상의 최종 결과
- 사이클 상한 도달, 사라진 처리 대상, 첫 관측 전달 실패의 결과 status와 failure code
- Backend 저장 확인을 첫 조작 조건으로 둘지 여부
- 책상 작업 담당자에게 반복을 맡기는 대안([260928 논의](<260928 - Table Cleanup Workflow.md>))의 최종 폐기 여부

## 7. 놓은 결과 확인에 관한 추가 의견

수거함 안착을 "확인됨 / 안 들어감 / 확인 못 함" 세 가지로 나누는 안이 제시됐다.
사용자는 실물에서 수거함 안착을 정확하게 확인할 방법이 없으므로, 일단 성공/실패
두 가지로만 두고 무엇으로 성공/실패를 판정할지는 추가로 고민해야 한다고 정리했다.
