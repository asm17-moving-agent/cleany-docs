# 261016 - System Supervisor 책임과 안전 경계

## 결정

2026-10-16 구현 지시에서 사용자가 확정한 원칙에 따라 System Supervisor를 도입한다.
시스템 가용성 및 안전 관련 장애에만 개입하고 다음 경계를 유지한다.

1. 영향받는 Capability만 제한하되 시스템 안전을 보장할 수 없으면 전체 운영을 잠근다.
2. Supervisor는 복구 정책과 실행 여부를 결정하고, 실제 복구는 담당 컴포넌트가 수행한다.
3. 복구 뒤 환경과 작업 상태의 재검증, Mission 재개 또는 재계획 판단은 Mission Manager가 한다.
4. 자동 복구에는 재시도 횟수와 시간 제한을 두고, 실패 시 기능 제한 또는 운영 잠금을 유지한다.
5. 시스템 운영 상태와 각 복구 작업의 진행 상태를 독립적으로 관리한다.

Supervisor는 실제 안전 정지와 하드웨어 보호를 소유하는 독립 안전 계층을 대체하지
않는다. 기존 Nav2 Recovery와 Lifecycle, Skill의 일반 실패 처리를 중복 구현하지 않는다.

이 기록의 근거는 사용자가 명시한 설계 원칙이다. 팀 전체 검토와 공유 기준 반영 여부는
GitHub PR에서 관리하며, 구현 완료나 실물 검증을 결정 승인과 동일하게 취급하지 않는다.

## 이유

- Mission 실행과 시스템 가용성 및 장애 정책의 책임을 분리한다.
- 일부 기능의 장애가 영향 없는 기능까지 불필요하게 차단하지 않게 하면서 안전이
  불확실하면 자동 운영을 허용하지 않는다.
- 기존 컴포넌트의 복구 기능을 재사용하고, Mission 재개에 필요한 환경 및 작업
  판단을 Mission 소유자에게 남긴다.

## 선택하지 않은 대안

| 대안 | 선택하지 않은 이유 |
|---|---|
| 시스템 상태와 장애 정책을 Mission FSM에 함께 집중 | 시스템 가용성 판단과 Mission 실행의 책임 분리 원칙에 맞지 않음 |
| 모든 Fault를 동일한 전체 잠금으로 처리 | 영향받는 Capability를 우선 제한하는 원칙에 맞지 않음 |
| Supervisor가 Skill 재시도와 Nav2 내부 복구를 직접 수행 | 컴포넌트 책임과 기존 복구 기능을 중복함 |
| 복구 Action 성공만으로 Mission을 자동 재개 | health 재검증과 Mission Manager의 재개 판단을 생략함 |

위 표는 명시된 원칙에서 제외되는 설계 방식이며, 별도의 비교 실험이나 팀 회의가
수행됐다는 기록은 아니다.

## 결과

- 시스템 운영 상태, 복구 작업 상태와 Mission 상태는 서로 다른 의미와 소유자를 갖는다.
- 허가는 실행 중 철회와 만료를 반영하고, Supervisor 재시작 시 이전 허가를 무효화한다.
- 중단 요청 수락, 실제 정지 확인, 복구 결과와 health 복귀를 구분해야 한다.
- E-stop 해제와 실제 정지 보장은 software reset 및 Supervisor의 생존에 의존하지 않는다.
- 정확한 메시지, TTL, 횟수, timeout, 필수 기능 집합과 장치별 연결은 구현 및 설정
  계약으로 관리한다. 이 Decision에서 특정 수치나 하드웨어 검증 완료를 확정하지 않는다.

2026-08-06의 별도 Local Guard를 두지 않는 결정은 행동별 allowlist 및 물리 제약 검증
경계를 다룬다. 이번 Supervisor는 그 검증을 옮기는 Guard가 아니라 시스템 가용성과
복구 조정의 소유자이므로 기존 Planner, Skill 및 하위 안전 책임을 유지한다.

## 재검토 조건

실제 컴포넌트 및 안전 adapter 통합에서 위 책임 경계를 유지할 수 없거나 복구 정책과
명령 소유권이 충돌하면 해당 근거를 기록하고 경계를 재검토한다. 실물 검증이 남아
있다는 사실을 정상 동작 가정으로 대체하지 않는다.
